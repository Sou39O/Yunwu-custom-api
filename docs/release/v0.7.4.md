# v0.7.4 修复生成结果落盘与批量下载卡住

## 概述

修复两个互相放大的问题：生成结果在实际网络环境下**根本没能保存到本地**，以及批量下载遇到失效远端链接时**看起来卡死**。

## 根因

### 1. 生成结果没落盘：Node 的内置 fetch 不走代理

Node 的 `fetch`（undici）**不读代理环境变量**——只有调用方显式传 `dispatcher` 时才走代理。而大多数用户只在代理软件里开了 Windows「系统代理」，没有配置 `HTTP_PROXY` / `HTTPS_PROXY`。

结果是服务进程直连境外图片 CDN（`imgen.x.ai`）一直连接超时，下载字节失败后作品只能退化成一条上游临时链接：

```
metadata: { storage: "remote-url" }   storageKey: null
```

链接过期后这些作品既下载不了、也显示不出来。

### 2. 批量下载卡在「打包中」

下载链路同样用全局 `fetch` 且**没有超时**。失效链接不会快速失败，而是一直挂着直到 TCP 超时（实测每张约 10.7 秒）。又因为是串行逐个下载，153 张就要 25 分钟，用户看到的就是永远停在「打包中」。

## 修复

### 服务进程接入系统代理

新增 `apps/desktop/src/main/system-proxy.ts`：启动内置服务前读注册表里的 `ProxyEnable` / `ProxyServer` / `ProxyOverride`，转成 `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY` 注入子进程。

- 用户已经显式配置了代理环境变量时**不覆盖**，尊重手动设置
- 自动把 `127.0.0.1` / `localhost` 及内网段放进 `NO_PROXY`，不影响本机请求
- 探测失败不影响启动

### 自己实现的代理下载器

新增 `apps/api/src/api/storage/proxy-fetch.ts`：因为全局 fetch 不走代理，改为按环境变量建 CONNECT 隧道，隧道内手写 HTTP/1.1 报文收发。

- 只用 Node 标准库，不引入新依赖（`https-proxy-agent` 在本仓库只是间接依赖）
- 遵守 `NO_PROXY`，支持重定向、chunked 编码、`content-length`
- SOCKS 代理给出明确提示，而不是静默失败

> 说明：实测发现 Node 的 `http.request` / `https.request` 在「自己接管的已握手 socket」上并不可靠（会 ETIMEDOUT），所以隧道内改为直接写报文，而不是复用内置请求器。

### 下载超时与并发

- 单个远端作品 20 秒超时，失效链接不再无限期占住下载
- 改为 8 路并发预取、按原顺序写入 zip，等待时间从「张数 × 超时」压到一两轮

## 实测结果

用真实数据的**隔离副本**验证（全程未触碰原始数据库）：

| 项目 | 修复前 | 修复后 |
| --- | --- | --- |
| 今天生成的 68 个作品 | 全部未落盘 | 全部补存成功 |
| 46 个作品（含 17 个过期项）批量下载 | 卡住不返回 | 2 秒完成，12.9 MB |
| 单个失效链接判定 | 挂起到 TCP 超时 | 0.7 秒判定失效 |
| 服务进程环境 | 无代理变量 | 自动注入 7897 代理 |

数据佐证：今天新生成的 68 个作品走代理全部返回 200（约 0.7 秒、300KB 真实图片），说明链接本身有效，此前纯粹是服务进程连不上。

## 已知限制

**已过期且从未落盘的作品无法找回。** 若上游临时链接在补存前就已失效（4xx），图片字节已不存在于任何地方。当前库中这类记录会被跳过，并在下载包里以 `README.txt` 说明数量。

## 升级说明

- 数据库无 schema 变更
- 桌面用户可在应用内更新到 0.7.4
- 升级后首次启动会自动补存存量的「仅上游 URL」作品；链接仍有效的会全部救回
- 若使用 SOCKS 代理，请在代理软件里开启 HTTP 代理端口，或在环境变量里显式指定 HTTP 代理
